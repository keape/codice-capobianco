# Censimento Obblighi QTSP — mappa

## Destination

Uno strumento — separato da `RAG-QTSP/sgsi-rag` ma affiancato ad esso — in produzione, che censisce in un knowledge graph gli obblighi normativi applicabili ai servizi fiduciari qualificati (QTSP) **e i principi/effetti giuridici dichiarativi di eIDAS/CAD in generale** (es. valore probatorio ed equivalenza legale delle firme elettroniche — vedi [issue 08](issues/08-estensione-principi.md)), a partire da un pilota su eIDAS + CAD. Lo strumento deve: popolare il censimento tramite estrazione LLM guidata da Claude Code + validazione umana obbligatoria; rispondere a domande in linguaggio naturale con un approccio ibrido (filtro faceted sui metadati, poi ranking semantico sul sottoinsieme); monitorare automaticamente i cambiamenti delle fonti normative nel tempo; esporre il tutto via tool MCP (uso conversazionale) + una UI web (consultazione, coda di revisione bozze, badge di monitoraggio).

Il traguardo del pilota è che le risposte a dubbi operativi *reali* (non di test) risultino affidabili e complete — copertura degli obblighi e qualità delle relazioni tipizzate sono precondizioni necessarie ma non sufficienti.

## Notes

- Dominio: servizi fiduciari qualificati (QTSP) — normativa italiana (CAD), regolatoria UE (eIDAS/eIDAS2), standard di settore (ETSI, ISO — fuori dal pilota).
- Glossario e modello di dominio: [CONTEXT.md](../../Censimento-Obblighi-QTSP/CONTEXT.md).
- Decisioni architetturali registrate: [ADR-0001](../../Censimento-Obblighi-QTSP/docs/adr/0001-censimento-come-knowledge-graph.md) (knowledge graph, non tabella piatta), [ADR-0002](../../Censimento-Obblighi-QTSP/docs/adr/0002-sqlite-dietro-interfaccia-a-grafo.md) (SQLite dietro interfaccia a grafo astratta), [ADR-0003](../../Censimento-Obblighi-QTSP/docs/adr/0003-estrazione-solo-dentro-sessioni-claude-code.md) (nessuna chiamata LLM autonoma — estrazione sempre dentro una sessione Claude Code).
- Ogni sessione che lavora un ticket di questa mappa dovrebbe consultare CONTEXT.md e gli ADR sopra prima di procedere; per i ticket di tipo `grilling`, chiamare lo Skill tool per "grilling" e "domain-modeling".
- Vincolo permanente: nessun componente dello strumento detiene una propria API key verso un LLM in cloud (vedi ADR-0003). L'estrazione è sempre avviata da una sessione Claude Code.
- Vettore semantico: Qdrant embedded (stessa tecnologia di sgsi-rag), ma collection/progetto separato.
- Perimetro pilota: solo eIDAS (incl. eIDAS2 dove applicabile) + CAD. Fonti da EUR-Lex ed Normattiva rispettivamente, scaricate automaticamente; l'URL sorgente è un attributo della Fonte.
- Accesso: uso individuale per il pilota (nessuna gestione multi-utente/permessi).

## Decisions so far

- [Fonte eIDAS: acquisizione da EUR-Lex](issues/01-fonte-eidas.md): usare la versione HTML consolidata di EUR-Lex (CELEX `0`+originale+`-YYYYMMDD`), già segmentabile per articolo via `div.eli-subdivision[id^="art_"]`, con storico versioni consultabile per il monitoraggio; nessun vincolo di licenza (CC BY 4.0) blocca l'uso interno.
- [Fonte CAD: acquisizione da Normattiva](issues/02-fonte-cad.md): CAD reperibile su Normattiva in Akoma Ntoso XML (via export per-atto e via nuovo portale Open Data dati.normattiva.it, dati CC BY 4.0 da gennaio 2026) — usare AKN come fonte primaria invece di parsing HTML ad-hoc; versioni storiche accessibili via parametro data (`!vig=YYYY-MM-DD` o `dataVigenza=`) per il confronto automatico tra versioni.
- [Schema dati SQLite + interfaccia a grafo](issues/03-schema-dati.md): tabelle `fonti`/`obblighi`/`relazioni` con ID interi, enumerazioni tutte a lookup table, soggetto obbligato/destinatario multi-valore in un'unica tabella di giunzione `obbligo_soggetti` con colonna `ruolo`, relazioni direzionali (una riga per fatto), stato di validazione bozza esplicito (bozze rifiutate eliminate). Stack: Python + `sqlite3` stdlib (no ORM), interfaccia a grafo con dataclass tipizzate (`vicini`, `cammino` — solo il più corto, via `WITH RECURSIVE` calcolata al volo, no tabella di chiusura precalcolata).
- [Tool MCP](issues/04-tool-mcp.md): 8 tool granulari (`interroga_obblighi`, `scrivi_bozze_obblighi`, `monitoraggio_stato`, `obbligo_dettaglio`, `obbligo_vicini`, `obbligo_cammino`, `fonte_lista`, `valori_lookup`), coerenti con il pattern di `sgsi-rag`. Nessun tool sintetizza testo o chiama un LLM proprio (ADR-0003): `interroga_obblighi` restituisce solo risultati grezzi (faceted a lista OR/AND + ranking semantico), la sintesi resta alla sessione Claude Code chiamante; `scrivi_bozze_obblighi` persiste soltanto bozze già estratte dalla sessione (rifiuta valori di lookup sconosciuti, nessuna auto-creazione); contratto di `monitoraggio_stato` e di `scrivi_bozze_obblighi` completati dai ticket 05/06.
- [Confronto tra versioni di una Fonte](issues/05-diff-versioni-fonte.md): granularità per articolo (sfrutta la segmentazione già nativa di EUR-Lex/Normattiva, ticket 01/02), confronto testuale diretto tra due fetch datati (no diff semantico), nessuna soglia fuzzy — qualunque differenza genera notifica, dato il pilota mono-utente. Obblighi impattati individuati per match esatto `fonte_id`+`riferimento` (segnalati, non riscritti automaticamente). Nuova tabella `modifiche_rilevate`; `monitoraggio_stato` arricchito con `riferimento` modificato + `obblighi_impattati` per fonte.
- [Flusso di estrazione guidato da Claude Code](issues/06-flusso-estrazione.md): richiesta in linguaggio naturale ("estrai gli obblighi dall'articolo N della Fonte X"), sessione che chiama `valori_lookup` prima di estrarre, recupera il testo dell'articolo direttamente dalla `url_sorgente` (nessun tool dedicato), poi `scrivi_bozze_obblighi`. Coda di revisione = righe `obblighi` con `stato_validazione='bozza'` (nessuna tabella separata). Relazioni proposte verso Obblighi non ancora esistenti: accettate come campo opzionale di `scrivi_bozze_obblighi`, scartate silenziosamente con motivo esplicito in risposta (`relazioni_scartate`) se il nodo target non esiste — nessuna creazione di nodi segnaposto.
- [Estensione a Principio, secondo tipo di nodo](issues/08-estensione-principi.md): il censimento copre anche norme dichiarative che non impongono un comportamento a un soggetto (es. art. 25 eIDAS, non discriminazione della firma elettronica) — un caso reale testato sulla UI web (ticket 07) non trovava risposta perché la norma non era un Obbligo. Nuovo tipo di nodo "Principio" (tipo di principio + oggetto giuridico multi-valore, non soggetto obbligato), stesso grafo di relazioni tipizzate di Obbligo, `relazioni` diventa polimorfica senza FK sulle estremità ([ADR-0004](../../Censimento-Obblighi-QTSP/docs/adr/0004-principio-come-secondo-tipo-di-nodo.md)). Perimetro allargato a qualunque principio dichiarativo di eIDAS/CAD, non solo quelli legati a strumenti QTSP.
- [Tool MCP estesi a Principio](issues/09-tool-mcp-principi.md): da 8 a 10 tool. I tool di scrittura/lettura puntuale restano separati per tipo di nodo (nuovi `scrivi_bozze_principi`, `principio_dettaglio`); i tool di navigazione del grafo si generalizzano invece di duplicarsi (`obbligo_vicini`→`nodo_vicini`, `obbligo_cammino`→`nodo_cammino`, con discriminante `tipo_nodo`); `interroga_obblighi`→`interroga_censimento` restituisce entrambi i tipi discriminati, perché una domanda in NL non sa a priori quale tipo di nodo le risponde; `monitoraggio_stato` cerca "nodi impattati" tra Obblighi e Principi.

## Not yet specified

- **Attributo "beneficiario" su Principio**: rimandato, non necessario per il caso che ha originato l'issue 08.
- **Ranking semantico congiunto Obbligo+Principio in `interroga_censimento`**: quando Qdrant sarà collegato, come pesare/ordinare insieme risultati dei due tipi di nodo — non ancora deciso (issue 09).
- **Estensione oltre il pilota**: ordine e modalità di aggiunta delle fonti successive (AgID, ETSI, ISO, GDPR) — alcune (ETSI, ISO) potrebbero non essere liberamente scaricabili come eIDAS/CAD, il che cambia il meccanismo di acquisizione e monitoraggio automatico già deciso per il pilota.
- **Evoluzione a un graph DB dedicato**: se/quando la scala (migliaia di nodi, query multi-hop frequenti) rende SQLite scomodo, come e quando migrare dietro l'interfaccia a grafo già prevista (ADR-0002).
- **Accesso multi-utente**: se il censimento si estende a tutto il team Compliance/Trust Services, servirà un concetto di ruoli/permessi e un audit trail più ricco del solo campo "validato da/data" attuale.
- **Metodologia di validazione del pilota**: come si costruisce concretamente il set di domande operative reali su cui giudicare il criterio di successo ("risposte affidabili e complete") — non ancora chiaro se sia un log delle domande poste durante l'uso ordinario o un set di test costruito apposta.
- **Localizzazione linguistica**: se serva gestire versioni multilingua dei testi (eIDAS esiste in tutte le lingue UE) o se il testo italiano/inglese di riferimento basti per il pilota.
